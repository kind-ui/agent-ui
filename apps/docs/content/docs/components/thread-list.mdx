## Composition

```text
ThreadList
├── ThreadListNew
├── ThreadListViewport
│   ├── ThreadListGrid
│   │   ├── ThreadListHeading
│   │   └── ThreadListRow
│   │       └── ThreadListLink
│   └── ThreadListEnd
│       └── ThreadListRetry
├── ThreadListMenu
│   └── ThreadListMenuContent
└── ThreadListDialog
    ├── ThreadListDialogError
    ├── ThreadListDialogCancel
    └── ThreadListDialogDelete
```

`ThreadList` renders these parts when you pass no children: a `nav` named by its `label`. `ThreadListNew` is the **New chat** button. `ThreadListViewport` scrolls the rows, and `ThreadListGrid` renders a `ThreadListHeading` for each group and a `ThreadListRow` for each chat in view. A row holds the chat's `ThreadListLink`, with its title, status and unread marks and any summary and progress under them, how long ago it changed, and its More button. Pass a row a function of its link's `{ value, title }`, defined once outside a render, to replace what its link shows. `ThreadListEnd` shows after the rows while older chats load. `ThreadListMenu` is UI SDK's Menu, one for every row, and `ThreadListDialog` is the Alert Dialog that asks before a delete.

## Usage

### Threads

Pass `threads`, each with an `id` and a `title`, and optionally an `href`, an `updatedAt` (an ISO date-time), `pinned`, a `group`, a `status`, `unread`, a `summary` and a `progress`. With an `href`, a chat's row is a real link, so it opens in a new tab like any other. A `status` of `queued`, `running`, `awaiting-input`, `error` or `complete` shows the status mark, named "Queued", "Running", "Needs input", "Failed" or "Done", and `unread` shows a dot named "Unread". A long title is cut short with an ellipsis, and the link's name is the whole title.

Each row ends in how long ago its `updatedAt` was, in a few characters: "now", "5m", "2h", "3d", then the date, like "Nov 2". The time is for the eye only, since the row's group already says when, so a screen reader reads the title alone. On hover, on focus and while its menu is open, the row's More button takes the time's place, and on touch screens More always shows instead.

Pass the current chat's `id` as `value`, and its link gets `aria-current="page"`. You own `value`, as your router owns the route.

### Groups

Pinned chats come first, under **Pinned**. Then chats with a `group` gather under it, in the order each group first appears, like a project or a folder. The rest gather by `updatedAt`: **Today**, **Yesterday**, **Previous 7 days**, **Previous 30 days**, then each month this year, then each year. Inside a group, chats keep the order you pass.

Groups and times depend on the clock, so pass `now` (an ISO date or date-time) when the server renders the list, or its markup and the browser's may group the chats apart. Without `now`, server markup shows each row's date, and the browser counts from its own clock once the list mounts, again each minute. Set `timeZone` to decide which day a chat falls on (UTC by default), `locale` for the month and year names, and `groupLabels` to replace the fixed words, like `{ today: "Aujourd'hui" }`.

### Inbox of Background Runs

Agent runs that keep working after a person leaves are chats too. Set `groupBy="status"` to group them by what they need from the person rather than by date: **Needs you** (waiting for input or failed, then finished and unread), **Running** (running or queued), then **Done**, newest first. Pinned chats still come first, and a chat's `group` is left out. `groupLabels` renames them by key: `needs-you`, `running` and `done`.

A chat's `summary`, like "+120 −8 in 4 files", shows under its title, and once any chat has one, every chat's row is `--kind-thread-row-height-tall` (52px), so rows keep one height for scrolling. While a chat is `running`, its `progress` (0 to 1) shows as a thin bar along its row's foot. The bar is for the eye; the link's description reads the summary and "45% done".

Pass `onArchive` to offer **Archive** in the row menu, and `onReadChange` to offer **Mark as read** or **Mark as unread**, whichever the chat's `unread` calls for, with what it should become in `details.read`. Archiving is yours to do: remove the chat from `threads`, and focus moves to the row that takes its place. Return a promise from `onArchive` to lock archiving until it settles; a rejection is announced as "Chat not archived".

### Opening a Chat

A plain click on a link, or Enter, calls `onSelect` with the chat's `id`. Call `details.cancel()` to route inside your app instead; otherwise the link follows its `href`. A click with a modifier key opens the link elsewhere and doesn't call `onSelect`.

```tsx
<ThreadList
  threads={threads}
  value={chatId}
  onSelect={(id, details) => {
    details.cancel();
    router.push(`chats/${id}`);
  }}
/>
```

Pass `onNew` to show **New chat**, which calls it with `details.source` saying how it was pressed. Adding the chat and opening it is yours to do.

### The Row Menu

The More button opens the row's menu, and so do a right-click or a long press on its link, Shift+F10 and the context-menu key. It offers **Rename** with `onRename`, **Pin** or **Unpin** with `onPinChange`, **Mark as read** or **Mark as unread** with `onReadChange`, **Share** with `onShare`, **Archive** with `onArchive` and **Delete** with `onDelete`, each only while its callback is set. Without any of them, rows have no More button.

**Rename** turns the title into a text field. Enter saves and Escape cancels, and an empty title doesn't save. `onRename` gets the chat's `id` and `details.title`, and the row keeps showing your `title` until you change it. Return a promise to keep renaming locked until it settles; a rejection is announced as "Chat not renamed". F2 on a focused link renames it too.

**Pin** and **Unpin** call `onPinChange` with what the chat should become in `details.pinned`. **Share** calls `onShare`.

The menu opens as a popover beside the More button. With `presentation="auto"`, the default, it's a bottom sheet on small touch screens; pass `"popover"` or `"sheet"` to choose one. Under `prefers-reduced-motion`, or with `motion="reduced"`, it only fades, and with `motion="none"` it opens at once.

### Deleting

**Delete** opens a dialog that asks "Delete chat?" with the chat's title, focused on **Cancel**. Only the dialog's **Delete** calls `onDelete`, with `details.source`. Return a promise to keep the dialog open until it settles, with both answers disabled and Escape waiting. When it resolves, the dialog closes. A rejection keeps it open with "Couldn't delete. Try again." beside the answers, and screen readers hear "Chat not deleted".

Set `confirmDelete={false}` to skip the dialog when you offer Undo instead. Either way, once the chat leaves `threads`, focus moves to the next row, else the one before it, else **New chat**.

### Keyboard

The list is one Tab stop. Up Arrow and Down Arrow move between chats, skipping headings, and Left Arrow and Right Arrow move between a chat's link and its More button, mirrored in right-to-left. Home and End go to either end of the row, Ctrl+Home and Ctrl+End (Cmd on a Mac) to the first and last chat, and Page Up and Page Down by a screenful. Typing the first letters of a title moves to it.

### Long Histories

Only the rows in view render, at a fixed height of `--kind-thread-row-height` (36px), so a list of thousands scrolls like a short one. Set `hasMore` and pass `onLoadMore` to load older chats: it's called once as the list nears its end, with `details.reason` set to `end-reached`. While they load, set `status="loading"` to show "Loading more chats" after the rows. If loading fails, set `status="error"` to show "Couldn't load more chats" and **Retry**, which calls `onLoadMore` again with `retry-press`.

### Agent

An agent connected with `createAgent` finds the list by its label and reads `value`, the current chat. It lists the chats by `id` and title, and every action takes a chat's `id`, refusing an unknown one. Each action is offered only while its callback is set, and `rename` and `archive` also only while none is pending. `markRead` marks a chat read, or unread with `false`. `select` calls `onSelect` and follows the link unless it's cancelled. `delete` opens the same dialog a person sees, whose **Delete** always needs a person to confirm, unless the host's `allow` lets it through; with `confirmDelete` off it calls `onDelete` at once.
