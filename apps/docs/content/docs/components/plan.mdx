Use a plan when an agent lays out its steps before it starts, and to follow them as it works. It shows each step with its status, how many are done, and an Accept button while you offer one, which "Accepted" replaces once the plan is accepted.

```text
│       └── PlanItem

│           ├── PlanItemTitle
│           └── PlanItemDescription
├── PlanAccept
└── PlanOutcome
    └── PlanOutcomeIcon
```

`Plan` renders the trigger, content, Accept button and outcome when you pass no children. Its trigger is a native button that shows or hides the list. `PlanTitle` shows the `label`, or "Plan" without one, and `PlanMeta` how many steps are done, like "2 of 5". `PlanList` renders an item for each of the `items` when you pass it no children, and each item shows its status mark, title and description. `PlanAccept` renders only while `onAccept` is set and the plan isn't accepted, and `PlanOutcome` only once it is. `PlanProgress`, a UI SDK Progress labeled "2 of 5 steps" that stays in view while the plan is closed, isn't in the default parts; compose it under the trigger if you want a bar.

## Usage

### Items

Pass the steps as `items`, each with an `id`, a `status` of `pending`, `running`, `complete` or `skipped`, a `title` and an optional `description`. Update an item's `status` as it runs, and keep its `id`: focus follows the id. Complete and skipped steps count as done, and a skipped step's title is struck through.

Without a `status` of its own, the plan's status is what the items add up to: `complete` once all are done, `running` once one runs or is done, and `pending` before that. Pass `status="awaiting-input"` while the plan waits to be accepted.

### Accepting

Pass `onAccept` to show **Accept plan**. Return a promise to keep the button pending until it settles: it keeps its label beside a running mark, a second press does nothing meanwhile, and a rejection makes it available again. Once the call resolves, **Accepted** takes the button's place at its height, and focus moves to it if the button had it. Pass `accepted` to say so yourself, for a plan accepted earlier or elsewhere. Leaving `onAccept` out instead removes the button with nothing in its place, and focus moves to the trigger.

### Opening and Closing

The plan opens and closes like a [Step](./step.mdx): it opens while it runs or waits for input and closes when it completes, until someone opens or closes it. Pass `open` with `onOpenChange` to control it.

### Keyboard

The items are one Tab stop. The arrow keys move between them, and Home and End go to the first and last. When the focused item is removed, focus moves to its neighbor. Screen readers read each item's status, then its title, and the running one as the current step.

### Streaming

A new item fades in once as it arrives, at the end of the list. A status change morphs only the item's mark and counts it in the meta, so the rows never shift. A removed item leaves at once. Screen readers hear an item's title and its outcome when it completes, and the plan's when it needs input or completes, in one message.

### Motion

Marks morph between statuses, and the list grows open and shut. Under `prefers-reduced-motion`, or with `motion="reduced"`, the list and marks fade over 120 ms instead and nothing moves or spins, and with `motion="none"` everything changes at once.

### Agent

An agent connected with `createAgent` finds the plan by its title and reads its `open` and `status`. It can run these actions, and `accept` only while Accept shows. While `agentConfirm` is on, every one of them waits for a person to confirm, unless the host's `allow` lets it through.
